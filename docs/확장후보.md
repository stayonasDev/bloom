# Handover 확장 후보 정리 (MVP 코드는 건드리지 않는다)

작성: 민수, 2026-10-24 14:40. MVP(인터뷰 → Claude 추출·일반화 → 블라인드 카드 → 수요문 매칭 → Sealed Q&A → 목업 구매)는 프로덕션에서 검증됐다(시드 15종 평균 38초, verify 29항목 통과). 아래는 "확장 후보"이며 구현은 지시가 있을 때 ② 태그 → ③ 번역 → ① 성과 수치 순으로 하나씩 한다. 목 데이터는 세 후보 모두 `mock/`에 먼저 들어가 있다(`tags.json`, `preseed/`, `requests-board.json`, `translations.json`, `sellers/*.self_reported`).

## 2) 태그 사전

축은 3개. 카드마다 field_key 1개(고정), topics 3~5개(그 직군 사전 안에서만), judgments 1~3개(공통). 언어·연차·난이도·희소도·가격·수입 경로 상태는 이미 카드 필드라 태그로 만들지 않고 필터 칩으로만 쓴다. 원본은 `mock/tags.json`이며 백엔드 `lib/tags.ts`는 이 파일을 그대로 복사한다.

**field_key (11)**: customer_support · billing_disputes · ecommerce_returns · hospital_intake · insurance_claims · accounts_payable · travel_booking · hr_screening · legal_assistant · content_moderation · other

**topics (직군별)**
| field_key | topics |
|---|---|
| billing_disputes | proration · roaming_waiver · loyalty_credit · plan_change · family_plan · retention_offer · contract_fee · late_fee · autopay_failure · early_termination · data_overage · sim_swap |
| ecommerce_returns | item_not_received · packing_error · courier_theft · return_window · partial_refund · voucher_payment · wrong_item · fraud_signal · marketplace_policy · damaged_in_transit |
| hospital_intake | insurance_mismatch · referral_required · no_show · walk_in_triage · copay_dispute · eligibility_check · prior_authorization · emergency_routing |
| insurance_claims | missing_document · claim_window · pre_existing_condition · partial_approval · fraud_signal · appeal_routing · policy_lapse · duplicate_claim |
| accounts_payable | three_way_match · duplicate_invoice · tolerance_override · approval_limit · month_end_cutoff · vendor_dispute · early_payment_discount · tax_code_error |
| travel_booking | change_fee_waiver · no_show_refund · schedule_change · name_correction · partial_cancellation · weather_exception · fare_rule_conflict · group_booking |
| customer_support | account_lockout · password_reset · service_outage · goodwill_credit · repeat_contact · abusive_caller · language_barrier · callback_promise |

**judgments (공통 7)**: refusal · exception · threshold · escalation · evidence · timing · de_escalation

**태그를 만드는 방법 (추출 호출 ②에 추가)**
- 프롬프트 추가분: "Also classify the note, choosing ONLY from the dictionary. Never invent a tag. field_key: exactly one. topics: 3 to 5 from that field's list. judgments: 1 to 3, strongest first. Output adds tags:{field_key, topics, judgments}."
- 서버에서 topics를 사전과 교집합으로 한 번 더 거른다(other 제외). 교집합 뒤 3개 미만이면 그대로 둔다(억지로 채우지 않음).
- 시드 5종의 기대 태그는 `mock/sellers/*.json`의 `expect_tags`에 있고, verify 기준은 field_key 일치 · topics 2개 이상 일치 · judgments 1개 이상 일치 · 사전 밖 0개다.

## 3) 검색과의 결합

검색은 하나다. 태그는 기존 수요문 매칭 **앞에 얹는 필터 한 겹**이고 수요문 매칭 자체는 바뀌지 않는다.

| 원칙 | 내용 | 응답 필드 |
|---|---|---|
| 1 역할 분리 | 태그 필터는 후보를 줄이고, 수요문 매칭은 그 안에서 순위를 매긴다. 필터를 안 고르면 지금처럼 전체 카드가 후보 | `applied_filters` |
| 2 사용자 우선 | 사용자가 고른 필터와 Claude가 수요문에서 읽은 태그가 다르면 사용자 것이 이긴다. 대신 `demand_tags`를 같이 돌려줘 프론트가 "수요문은 ecommerce_returns로 읽혔습니다. 필터를 풀까요?" 한 줄을 띄운다. 필터가 없을 때는 `demand_tags`를 결과 위 칩으로 보여 주고 클릭하면 필터가 된다 | `demand_tags` |
| 3 0건 금지 | 필터로 후보가 0건이면 비우지 않고 topics → judgments 순으로 하나씩 풀어 다시 찾는다. 풀어낸 조건을 돌려준다. field_key는 풀지 않는다(사용자 명시) | `relaxed_filters` |
| 4 점수는 수요문 기준 | 태그 일치만으로 점수를 주지 않는다. 태그는 이유 문장의 근거("packing_error, item_not_received 겹침")로만 쓴다 | `matches[].reason` |

**매칭 호출 ③ 변경**
- 입력: 수요문 + filters + 후보 카드(필터 적용 후, 공개 필드 + 태그 + 항목 수). 인계서 원문은 지금처럼 보내지 않는다.
- 프롬프트 추가분: "First tag the demand the same way (1 field_key, 2–4 topics, 1–2 judgments). Score 0–1 weighing in order: topic overlap, same field_key, judgment overlap, rarity. A card with no topic overlap and a different field_key must score below 0.3. reason: one line under 120 characters naming the overlapping tags. Output: {demand_tags, matches}."
- 후보 50장 초과 시 field_key로 먼저 거른 뒤 보낸다. 지금 프로덕션은 약 40장이라 아직 안 걸린다.
- 검증: `mock/requests-board.json` 4종(다른 분야 카드 < 0.3)과 `mock/requests.json`의 no-match-forklift(전부 < 0.5). 프로덕션 실측은 0.06·0.04·0.03이었다.

**프론트 흐름**: 목록 화면에서 직군 드롭다운 1개 + 판단 유형 칩 7개를 고르면, 같은 필터가 수요문 입력 화면까지 이어진다. 카드에는 태그 칩 한 줄(topics 3~5). 매칭 결과 위에 demand_tags 칩, 완화가 있었으면 "topics 조건을 풀어 찾았습니다" 한 줄.

## 4) 바꿀 곳 (DB·API·프롬프트)

| 후보 | DB (`supabase/migrations/0002_*.sql`) | API | 프롬프트 |
|---|---|---|---|
| ② 태그 | `alter table cards add field_key text, add topics text[] default '{}', add judgments text[] default '{}'; create index cards_topics_gin on cards using gin(topics); create index cards_field_key_idx on cards(field_key);` preseed 8장과 시드 카드는 백필 스크립트 1회(`tags` 필드를 `mock/preseed/*.json`·`expect_tags`에서) | `POST /api/requests` 요청에 `filters:{field_key?, topics?[], judgments?[]}` 선택. 응답에 `demand_tags`, `applied_filters`, `relaxed_filters`. `GET /api/cards`에 `field_key`, `topics`(쉼표), `judgments` 쿼리. `GET /api/cards/{id}`·seal 응답 card에 `tags`. 사전은 `lib/tags.ts` 한 파일, `mock/tags.json`과 동일 내용 | 추출 ② 분류 추가분, 매칭 ③ 태깅·가중치·0.3 규칙 추가분 (2절·3절 원문) |
| ③ 번역 | `create table pack_translations(pack_id uuid references packs, lang text check (lang in ('ko','ja')), card_one_liner text, handover_note jsonb, created_at timestamptz default now(), primary key(pack_id, lang)); alter table sealed_qa add answer_translations jsonb default '{}';` | `GET /api/cards?lang=ko` → one_liner 번역본(없으면 영어). `GET /api/packs/{id}/note?lang=` → 봉인 규칙 동일. `POST /api/cards/{id}/ask` 응답에 `answer_translations:{ko,ja}`. 봉인 시 번역 2회 호출은 seal 라우트 안에서 추출 뒤 순차(maxDuration 120 안), 실패하면 번역 없이 201 | 호출 ⑤ 신규: "Translate for a customer-support professional. Keep every number, amount, currency, duration, date, percentage and threshold exactly as written. Keep practitioner terms (proration, chargeback, prior authorization) in English with a short gloss on first use. Do not add, drop, or soften any rule. JSON only." 입력 `{texts:[{id,text}], target}` → 출력 `{translations:[{id,text}]}` |
| ① 성과 수치 | `alter table sellers add self_reported jsonb;` | `POST /api/sellers` 요청에 `self_reported:{cases_per_month, escalation_rate_pct, years_on_queue}` 선택(범위 검사만, 범위 밖도 저장). 카드 응답과 매칭 card에 `self_reported` + `verification:"self_reported"` | 없음 |

공통: `docs/API.md`·`docs/DB.md`에 위 필드를 추가하고 인계사항에 "합의" 뒤 제안자가 고친다. 검증은 `npm run verify:mock`의 tags·board·translate 묶음이 API가 생기면 자동으로 켜진다(지금은 SKIP).

## 5) 가정과 미정 사항

- 태그 사전은 `mock/tags.json`이 원본이고 `lib/tags.ts`는 복사본이다. 둘이 어긋나지 않도록 verify `tags` 묶음이 사전 밖 태그 0개를 검사한다. 사전을 바꾸면 두 파일을 같이 바꾼다.
- 번역은 KO·JA 2개로 시작한다. 팩당 Claude 호출이 2회 늘고(추출 뒤 one_liner+인계서 번역 ko, ja), 봉인 응답이 약 10~20초 늘 수 있다. 실측 후 seal 안에서 할지 뒤에서 할지 정한다.
- 필터 완화 순서는 topics → judgments로 시작하고 샘플 돌려본 뒤 조정한다. field_key는 풀지 않는다.
- `sellers.language`가 EN/KO만 허용해 JA 카드(preseed legal-translation-ja)는 판매자 EN, 카드 JA로 들어가 있다. 번역 후보를 구현할 때 `language` 제약에 JA를 추가할지 정한다.
- 성과 수치의 범위 밖 값(예: 99999)은 거부하지 않고 저장한 뒤 라벨만 붙이는 것으로 가정했다. 범위 밖을 거부로 바꾸려면 `mock/broken/self-reported-absurd.json`의 expect를 바꾼다.
- 세 후보 모두 MVP 검증 뒤 지시가 있을 때만 구현한다. 이 문서는 그때까지 바뀌지 않는다.
